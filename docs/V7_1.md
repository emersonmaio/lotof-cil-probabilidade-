# V7.1 — processamento otimizado

V7.1 mantém as mesmas equações do V7 e muda a infraestrutura de cálculo para reduzir trabalho repetido. Não é uma nova estratégia estatística.

## O que foi otimizado
- Cada sorteio vira uma máscara de 25 bits.
- Acertos e sobreposição entre jogos usam operações de bits.
- Frequências dos 25 números usam prefix sums.
- Coocorrências dos 300 pares usam prefix sums.
- Recência usa a última ocorrência pré-computada.
- O estado de pontuação de cada configuração/concorrente é calculado uma vez e reutilizado entre seeds.
- A estabilidade V7.1 reutiliza os mesmos estados em todas as seeds.

## Risco de queda de produtividade
O principal risco é o tempo gasto na geração/seleção dos candidatos, não mais no cálculo do histórico. Por isso V7.1 mantém inicialmente 220 candidatos, exatamente o valor usado pelo V7. O número não foi aumentado até medir o tempo real.

A primeira comparação deve ser: métricas V7 x V7.1; tempo de execução; estabilidade entre seeds; depois testar 500/1000 candidatos se houver folga de processamento.

Não considerar uma mudança de desempenho como ganho estatístico até que a avaliação fora da amostra confirme.

## Integridade temporal
Para cada concurso-alvo, os estados são construídos somente com concursos anteriores ao alvo. O resultado do alvo não entra no cálculo do próprio portfólio.

## Execução
python src/v7_1_optimized.py --csv data/lotofacil.csv --out results/v7_1 --holdout-end 3794

Estabilidade:
python src/v7_1_stability.py --csv data/lotofacil.csv --out results/v7_1 --holdout-end 3794 --seeds 5

O workflow do GitHub Actions usa V7.1 como motor de produção; os arquivos V7 originais permanecem no repositório para auditoria/comparação histórica.
